# apps/web `getApiBase()` module-scope freeze — fix report

## Symptom

`apps/web` is now a single shared static export (`output: 'export'`) served
from the tenant Worker's own origin, instead of one build per tenant with the
API origin baked in. `apps/web/src/lib/api-base.ts` resolves the base at
call time: if `NEXT_PUBLIC_API_URL` is still the unsubstituted build
placeholder (`https://__LH_WORKER_URL__`), it falls back to
`window.location.origin` — but only when `window` exists.

Five call sites bound the result of `getApiBase()` to a module-scope
`const`. Next.js prerenders every `'use client'` page once in Node during
`next build` to produce its initial static HTML, and `window` is undefined
there. A module-scope const froze whatever `getApiBase()` returned during
that Node pass — for a shared build, the unresolved placeholder — for the
lifetime of the page, since ES module top-level code runs once and the
result is cached. The friend-add QR at `inflow-links/page.tsx:156`
(`` `${WORKER_BASE}/r/${refCode}` ``) encoded a broken URL as a result, and
`lib/api.ts`'s `API_URL` (the base for every general admin API call) had the
same problem.

## Sites fixed

All five were converted from a frozen module-scope constant to a function
invoked at call time, matching the pattern already used correctly at the
other 17 call sites in this codebase (e.g. `components/auth-guard.tsx`,
`app/login/page.tsx`, which call `getApiBase()` inside a handler/effect).

1. **`apps/web/src/app/updates/page.tsx`** — `const API_URL = getApiBase()!`
   → `function apiUrl(): string { return getApiBase()! }`, called as
   `apiUrl()` in `fetchHistory`'s single `fetch(...)` call.
2. **`apps/web/src/app/inflow-links/page.tsx`** —
   `const WORKER_BASE = getApiBase() ?? ''` → `function workerBase(): string`,
   called as `workerBase()` at the one call site building the friend-add
   link/QR URL (`onCopy`, line ~156).
3. **`apps/web/src/app/affiliates/page.tsx`** — `const WORKER_BASE =
   getApiBase(); if (!WORKER_BASE) throw ...` at module scope → moved into
   `function assertWorkerBaseConfigured(): void`, called as the first line
   of the `AffiliatesPage()` component body (the original guard was never
   otherwise consumed to build a URL in this file — it existed purely as a
   fail-fast check for a misconfigured build, which this preserves, just
   evaluated at call time instead of module-evaluation time).
4. **`apps/web/src/lib/api.ts`** — `const API_URL = getApiBase(); if
   (!API_URL) throw ...` at module scope → `function apiUrl(): string`
   (throws internally if unconfigured), replacing all 4 real usages
   (`fetchApi`'s base fetch, `externalImageUrl`, `uploadImage`, `imageUrl`
   under rich menus) with `apiUrl()` calls. This is the base for the admin's
   general API calls, so this was the widest-blast-radius site.
5. **`apps/web/src/lib/update-client.ts`** — same pattern, `function
   apiUrl(): string`, replacing 5 usages (`getManifestUrl`,
   `getCurrentVersion`, `startUpdate`, `getUpdateStatus`,
   `openUpdateStream`).

`api-base.ts` itself was **not** touched — its placeholder-vs-configured
precedence logic (an explicit non-placeholder `NEXT_PUBLIC_API_URL` still
wins) is unchanged.

## Guard added

New test: **`apps/web/src/lib/api-base-call-site.test.ts`**.

Since this repo has no ESLint configured for `apps/web` (only TypeScript +
Vitest), the guard is a Vitest test that statically scans every `.ts`/`.tsx`
file under `apps/web/src` for a module-scope (column-0 — this codebase is
prettier-formatted, so a function body is always indented) `const`/`let`/
`var` declaration whose initializer calls `getApiBase()`. It fails the test
suite if any file (other than `api-base.ts` and its own test) contains the
pattern.

**Proof it actually fails on the bad pattern**: reintroduced the exact
original defect into `apps/web/src/app/updates/page.tsx` (`const API_URL =
getApiBase()!` at module scope), ran the guard test, confirmed a failure,
then reverted the file back to the fix. Captured output:

## Verify

### Build + grep

```
$ pnpm --filter web build
...
✓ Compiled successfully in 3.6s
✓ Generating static pages (48/48)
✓ Exporting (2/2)

$ grep -rl "__LH_WORKER_URL__" apps/web/out
apps/web/out/_next/static/chunks/5040-60c518fb3f18967e.js
apps/web/out/_next/static/chunks/app/login/page-03a20e7c572608b4.js
apps/web/out/_next/static/chunks/app/updates/page-54f5918c044f0c8f.js
```

**Interpretation — this is not a regression.** I checked what's actually at
those hits rather than trusting the grep count:

- The placeholder string only appears as the definition of the exported
  `ADMIN_URL_PLACEHOLDER` constant itself (`var s="https://__LH_WORKER_URL__"`
  in each chunk, from `@line-harness/update-engine/pure`) — the literal is
  required in the bundle for `getApiBase()`'s own `configured !==
  ADMIN_URL_PLACEHOLDER` comparison to work at runtime. That comparison is
  the whole point of the runtime-resolution path, so its literal has to be
  present in the bundle; that's expected and desired.
- `grep -rno '__LH_WORKER_URL__[^"]*/admin[^"]*' apps/web/out` and a
  template-literal search both came back empty — there is **no** frozen
  fetch URL like `` fetch(`https://__LH_WORKER_URL__/admin/...`) `` baked
  into any chunk, and no `apps/web/out/*.html` file contains the placeholder
  literal at all (checked directly) — i.e. nothing prerendered froze the
  placeholder into the exported HTML.
- The `window.location.origin` fallback branch of `getApiBase()` is present
  in chunk `4937-e9b9b2a90c8c94ce.js`, which is loaded by all 32 exported
  pages including `inflow-links.html` and `affiliates.html` (checked via
  `grep -l 4937 apps/web/out/*.html` and per-page chunk references) — i.e.
  the runtime-resolution logic is reachable from the pages that were fixed,
  not dead code.
- No build env var (`NEXT_PUBLIC_API_URL`) was set for this local build, so
  `getApiBase()` returned `undefined` at build time for every one of the
  five previously-broken sites — under the old bug this would have baked
  `undefined`/empty strings into frozen constants; instead every fixed site
  now resolves lazily via a function, so the browser gets the real
  `window.location.origin` regardless of what was (or wasn't) set at build
  time.

## Concerns

- `apps/web/src/app/affiliates/page.tsx`'s `WORKER_BASE` was (and remains)
  unused for anything beyond the fail-fast guard — no URL in that file is
  actually built from it. Not part of this fix's scope, flagging for
  awareness only.
- `lib/api.ts`'s and `update-client.ts`'s "not configured" error messages
  were reworded slightly (`'Build cannot proceed...'` →
  `'Cannot resolve the API base URL...'`) since the check that used to run
  once at build/module-load now runs on every call in the browser too; the
  old wording would have been misleading if it ever surfaced as a runtime
  error in a browser console instead of a build failure.
