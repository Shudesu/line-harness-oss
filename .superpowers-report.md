# DO-based scheduler for the L Harness tenant Worker

## Binding name and class name (read this first)

- **Class name:** `TenantScheduler`
- **Binding name:** `TENANT_SCHEDULER`
- Implementation: `apps/worker/src/durable-objects/tenant-scheduler.ts`
- Declared in `apps/worker/wrangler.toml` (default env + `[env.production]`) **and**
  in `scripts/lib/tenant-wrangler.ts` (`renderTenantToml`, consumed by
  `scripts/lhc-provision.mts` / `scripts/lhc-update-tenant.mts` to build
  `wrangler.lhc.toml` for every managed tenant). Both places use the identical
  `name = "TENANT_SCHEDULER"` / `class_name = "TenantScheduler"` pair. I found
  `scripts/lib/tenant-wrangler.ts` to be the "separate system that provisions
  tenants" the task warned about — it renders each tenant's wrangler config
  from scratch (not copied from `apps/worker/wrangler.toml`), so the binding
  had to be added there explicitly or every newly-provisioned tenant would
  deploy successfully with no DO binding at all, and the alarm would never
  arm. A repo-wide gate test, `scripts/lhc-env-parity.test.ts`, independently
  caught this when I first forgot the `tenant-wrangler.ts` side — it now also
  verifies the classification (`via: 'binding'`) and had its detection regex
  extended to recognize `[[durable_objects.bindings]]`'s `name = "X"` syntax
  (previously it only knew `binding = "X"` from d1/r2).
- SQLite storage migration: `[[migrations]] tag = "v1"
  new_sqlite_classes = ["TenantScheduler"]` added in both wrangler.toml and
  the tenant template.

## Cadence mapping (from the old `scheduled()`)

The old `scheduled()` (now moved verbatim into `apps/worker/src/scheduled.ts`,
logic unchanged — only its *trigger* moved) had two cadences, disambiguated by
`event.cron`:

- **Minute cadence** (`event.cron === '* * * * *'`): everything except the
  blocks explicitly gated on `'0 */6 * * *'` — account/token refresh, broadcast
  recovery, booking/event/meet/webinar reminders and followups, the
  queued/scheduled/step broadcast jobs, reminder delivery, account health
  check, insight fetch, and (only when `now.getUTCMinutes() % 5 === 0`) the
  mileage queue drain.
- **6-hour cadence** (`event.cron === '0 */6 * * *'`): following-mileage
  milestone enqueue, booking expirer, event-booking expirer, and (if
  `LOG_RETENTION_DAYS` is set) log retention.

`TenantScheduler.alarm()` re-arms every 60s (`SCHEDULER_TICK_INTERVAL_MS`) and
calls the *same* `scheduled()` with a synthesized event:
- Every tick: `{ cron: '* * * * *', scheduledTime: now }`.
- Additionally, when `isSixHourBoundary(now)` (UTC minute === 0 and
  `hour % 6 === 0`): `{ cron: '0 */6 * * *', scheduledTime: now }` — a second
  call, in the same tick.

I deliberately reproduced Cloudflare's actual Cron Trigger behavior rather
than inventing a new shape: with two configured cron patterns, at the minute
where both match, Cloudflare invokes `scheduled()` **twice** (once per
matching trigger). The DO does the same. This is why the double-run question
below has a real, currently-in-production precedent to point to.

## Double-run prevention (DO alarm + Cron Trigger coexisting)

No new locking was added. The existing job bodies are already required to
tolerate concurrent/duplicate invocation, because **today's single-cron-only
setup already double-invokes `scheduled()` at every 6-hour boundary** (both
triggers fire in the same minute). That's proven by e.g.
`apps/worker/src/services/broadcast.ts`'s optimistic claim:
`UPDATE broadcasts SET status = 'sending' WHERE id = ? AND status = 'scheduled'`
— a second concurrent runner simply claims 0 rows. Booking/event reminders,
recovery, and quota batching all follow the same claim-by-WHERE-clause
pattern. Since DO-triggered and Cron-triggered calls both go through the same
`scheduled()` → same job functions → same D1 claim statements, self-hosted
deployments that keep Cron Trigger enabled alongside the DO get the same
safety property for free. I did not invent a new guarantee; I verified the
existing one already covers this case and said so in code comments
(`durable-objects/tenant-scheduler.ts` top-of-file comment, "二重発火の扱い").

## Re-arm-before-work ordering (proof)

`runSchedulerTick()` in `tenant-scheduler.ts`:
1. `await storage.setAlarm(now + SCHEDULER_TICK_INTERVAL_MS)` — unconditional,
   first statement.
2. Only then: `try { await runJobs(...) } catch (err) { console.error(...) }`
   — the work runs inside a try/catch that swallows (does not re-throw).

Swallowing matters as much as the ordering: if `runJobs` threw and that
exception propagated out of `alarm()`, the DO runtime's own automatic alarm
retry would fire *in addition to* the next alarm already armed in step 1,
risking a second kind of double-run this task didn't ask for. Catching
locally means a failed tick costs exactly one tick, is logged, and the
already-armed next alarm is the only thing that fires next.

Constructor-level defense-in-depth (not explicitly required, added for
robustness): `TenantScheduler`'s constructor calls
`ctx.blockConcurrencyWhile(() => ensureAlarmArmed(ctx.storage))`, so the very
first touch of a fresh DO instance (via any code path, not just the webhook
self-heal RPC) arms it.

## Self-heal

`ensureSchedulerArmed(env)` in `tenant-scheduler.ts` is called from
`apps/worker/src/routes/webhook.ts` via `c.executionCtx.waitUntil(...)` (added
as a second `waitUntil` call, after the existing event-processing one, so it
never delays the ~1s LINE webhook response and doesn't disturb existing tests
that assert on `waitUntil.mock.calls[0]`). It resolves a single fixed-name DO
instance (`idFromName('scheduler')` — one scheduler per tenant Worker) and
calls its `ensureArmed()` RPC method, which does one `getAlarm()` and only
`setAlarm()`s if missing. Both `ensureSchedulerArmed` and `ensureArmed()`
swallow their own errors so a self-heal failure never affects the webhook
response.

## What moved vs. what changed

`scheduled()` itself was **not rewritten** — it was cut out of `index.ts`
verbatim (comments, ordering, try/catch blocks, all identical) into
`apps/worker/src/scheduled.ts` and exported, purely so the DO file can import
it without a circular dependency back through `index.ts` (which now
re-exports `TenantScheduler`). `index.ts`'s only changes: the import block
lost symbols that were exclusively used inside the old `scheduled()`, gained
`import { scheduled } from './scheduled.js'` and
`import { TenantScheduler } from './durable-objects/tenant-scheduler.js'`,
the `Env.Bindings` type gained `TENANT_SCHEDULER`, and `export { TenantScheduler };`
was added (Wrangler requires the DO class to be a named export of the
`main` entry file for same-script bindings).

Cron Trigger config (`[triggers]` / `scheduled()` / `[[migrations]]` are
additive) is untouched and still present in both wrangler.toml environments
and the tenant template.

## Uncertainties / things worth a second look

- I could not run this under a real Durable Object runtime (no
  `@cloudflare/vitest-pool-workers` in this repo), so `TenantScheduler`'s
  class-level tests use a hand-rolled fake `DurableObjectState`
  (`storage.getAlarm/setAlarm`, `blockConcurrencyWhile`) rather than the real
  thing. The pure-function core (`runSchedulerTick`, `ensureAlarmArmed`,
  `isSixHourBoundary`) is what actually carries the correctness guarantees
  and is tested directly against the real `AlarmStorage` contract shape.
- Tenant deployments' Cron Trigger cadence (`*/5 * * * *`, not `* * * * *`)
  differs from the dev/prod wrangler.toml (`* * * * *`). I left this as-is —
  it's pre-existing, unrelated to this task, and the DO now drives the
  primary 1-minute cadence for all deployments regardless, with cron staying
  as a slower self-hosted-only fallback. Worth flagging in case that cadence
  difference was accidental rather than intentional, since it's now double
  redundant-but-still-live infrastructure.

# Runtime resolution of the admin UI's API base (shared-build support)

## Problem recap

`apps/web` (the admin UI, Next.js `output: 'export'`) read `NEXT_PUBLIC_API_URL`
at build time, baked into the bundle as a literal string. That's why the
provisioning path ran a full `next build` per tenant. A shared build (one
build, reused by every tenant) can't know the real Worker URL at build time,
so it's built with the placeholder `https://__LH_WORKER_URL__` and never
materialized. Left as-is, every API call in that build would try to hit
`https://__LH_WORKER_URL__/...` and silently fail. In the new layout the
admin is served by the tenant Worker itself (same origin as the API), so the
fix is: read the API base at runtime, and if the placeholder was never
substituted, fall back to `window.location.origin`.

## How the existing placeholder convention works (reused, not reinvented)

`packages/update-engine/src/materialize.ts` already defines
`ADMIN_URL_PLACEHOLDER = 'https://__LH_WORKER_URL__'` and
`materializeAdminFiles()`, which does a literal string-replace over every
text asset in a per-tenant/self-hosted admin bundle, swapping the placeholder
for the install's real Worker origin, before the files are ever served. That
mechanism is untouched — it's still exactly how per-tenant builds and
self-hosted installs resolve their URL, and it's still the reason a shared
build's bundle contains the *unsubstituted* placeholder (nothing rewrites it,
because one shared build has no single "real" URL to bake in).

I extracted the constant itself into a new tiny file with no Node
dependencies, `packages/update-engine/src/admin-url-placeholder.ts`, and had
both `materialize.ts` (Node-side, used by the CLI/Worker materialization
logic) and `pure.ts` (browser-safe entry point, already consumed by
`apps/web/src/lib/update-client.ts` for the self-update UI) import/re-export
it from there. This keeps the browser and the Node-side materializer using
the literal *same* string constant instead of two independently-typed copies
that could drift. `packages/update-engine/dist/*` was rebuilt (`npm run
build` inside `packages/update-engine`) so the new export is live; `dist/`
is gitignored so nothing needed to be committed there.

## Every place that reads the API base, and what I did with each

I grepped `process.env.NEXT_PUBLIC_API_URL` across `apps/web/src` and found
15 read sites across 13 files. All were consolidated to call one new
function, `getApiBase()` in `apps/web/src/lib/api-base.ts`, instead of
touching `process.env.NEXT_PUBLIC_API_URL` directly:

- `apps/web/src/lib/api.ts` — `fetchApi`, rich-menu image URLs (`externalImageUrl`, `imageUrl`), `uploadImage`. Module-level `const API_URL = getApiBase()`, still throws if unset (unchanged behavior).
- `apps/web/src/lib/update-client.ts` — manifest URL, version/start/status fetches, and the update-progress `EventSource` (SSE, closest thing to a "websocket" read site here). Same throw-if-unset pattern preserved.
- `apps/web/src/app/page.tsx` — friend-add share link.
- `apps/web/src/app/pools/page.tsx` — public pool URL shown to the operator.
- `apps/web/src/app/booking/bookings/page.tsx`, `booking/menus/page.tsx` — LIFF booking share URLs.
- `apps/web/src/app/updates/page.tsx` — update-history fetch (`getApiBase()!`, preserving the pre-existing non-null assertion).
- `apps/web/src/app/inflow-links/page.tsx`, `inflow-links/detail/page.tsx` — tracked-link/ref-code share URLs.
- `apps/web/src/app/affiliates/page.tsx` — throws at module load if unset (preserved).
- `apps/web/src/app/login/page.tsx` — login fetch, inside the submit handler.
- `apps/web/src/components/auth-guard.tsx` — session-check fetch, inside a `useEffect`.
- `apps/web/src/components/layout/sidebar.tsx` — logout fetch, inside an `onClick` handler.
- `apps/web/src/components/accounts/account-setup-urls.tsx` — webhook/OAuth/LIFF registration URLs shown for the operator to paste into LINE Developers Console.
- `apps/web/src/components/events/event-form.tsx` — LIFF event share URL.

`getApiBase()` preserves each call site's original "what to do if unset"
behavior exactly (throw / `?? ''` / early-return with a UI error / `!`
assertion) — only *how the configured value is computed* changed, per the
task's instruction not to change what any API call does.

### `getApiBase()` precedence (in `apps/web/src/lib/api-base.ts`)

```ts
export function getApiBase(): string | undefined {
  const configured = process.env.NEXT_PUBLIC_API_URL
  if (!configured || configured !== ADMIN_URL_PLACEHOLDER) {
    return configured
  }
  return typeof window !== 'undefined' ? window.location.origin : configured
}
```

1. Unset → `undefined` (same signal as before; callers decide what to do).
2. Set to something other than the placeholder → that value, unchanged
   (per-tenant build / self-hosted install path, byte-identical to today).
3. Still the placeholder + running in a browser → `window.location.origin`
   (the new shared-build path).
4. Still the placeholder + no `window` → returns the placeholder itself
   (see "non-browser read path" below — this never feeds an actual fetch).

## Non-browser read path (the thing the task asked me to check for)

`apps/web` uses `output: 'export'`. Every page/component that reads the API
base is `'use client'`, but `next build` still executes those modules once in
Node to prerender the initial static HTML (no `window` there) before the
browser hydrates and re-executes them for real. I verified two things stay
safe under that:

- `getApiBase()` never dereferences `window` unless `typeof window !==
  'undefined'` is already true — so it can't crash the Node-side prerender
  pass, regardless of whether it's called at module scope (e.g. `api.ts`,
  `update-client.ts`, `WORKER_BASE` constants) or inside a component's render
  body (e.g. `pools/page.tsx`'s `apiBase`).
- Every call site that could execute during that Node pass only ever uses the
  *value* for display (a link's `href`/text) or as a fetch's URL — and every
  fetch call site (`fetchApi`, `handleLogin`, `checkSession`, the logout
  handler, `fetchHistory`) lives inside an event handler or a `useEffect`,
  neither of which React runs during the Node-side render. So the branch that
  returns the raw placeholder in a non-browser context is only ever read for
  a one-time prerendered HTML snapshot that's about to be replaced by
  hydration — it never reaches an actual network call. I confirmed with a
  real `next build` (`NEXT_PUBLIC_API_URL=https://__LH_WORKER_URL__`) that
  static generation completes without error for all 48 routes.

I did not find any read of the API base in a persistent server-side runtime —
`output: 'export'` means there is no Next.js server for this app at all, only
the one-time Node build pass described above.

## A related, out-of-scope finding (not changed)

`apps/web/src/app/webhooks/page.tsx`'s `endpointUrl()` already does
`typeof window !== 'undefined' ? window.location.origin : ''` for the
incoming-webhook registration URL it shows the operator — but it never reads
`NEXT_PUBLIC_API_URL` at all, so it wasn't in scope for "every place that
reads the API base." Under the *old* topology (admin on a different host
than the Worker) this was arguably already wrong — the admin's own origin is
not the Worker's origin there. Under the *new* same-origin layout it happens
to be correct by accident. I left it untouched (changing it would mean
changing what that page displays, which the task said not to do) but flagged
it here in case it's worth a follow-up to route it through `getApiBase()` for
consistency.
