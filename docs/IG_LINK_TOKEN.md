# Instagram link tokens (`igt`, spec 08)

LINE Harness verifies IG Harness's signed link before linking a LINE friend to an Instagram scoped ID (IGSID). Default policy is `off`, preserving old unsigned `ig` links. An explicitly supplied invalid token never falls back to `ig`, under any policy. Friend registration and the rest of the LIFF flow continue.

## Wire format and key selection

IG Harness emits `<line-worker>/r/<short>?igt=<token>[&igan=<username>][&pool=<slug>]` without a raw `ig`. Update LINE Harness **before** updating the issuer: old LINE versions cannot link these token-only URLs.

```
payload = { v: 1, igsid: string, iga?: string, exp: unix_seconds, n: nonce }
payloadPart = base64url(UTF8(JSON.stringify(payload)))
igt = payloadPart + "." + base64url(HMAC_SHA256(key, ASCII(payloadPart)))
```

Both encodings use the URL-safe alphabet without padding. The nonce is the canonical 22-character base64url encoding of 16 random bytes. The receiver rejects noncanonical base64url, malformed UTF-8/JSON, noninteger expiry, wrong version, empty or over-128-character `igsid`/`iga`, malformed nonce, tokens longer than 8,192 characters, and expiry outside `now < exp <= now + 604800`. Verification uses Web Crypto `crypto.subtle.verify`, never a signature string comparison. `now` arguments in the reference TypeScript helpers use **milliseconds**, while payload `exp` uses seconds.

Key selection, in priority order:

1. If `IG_LINK_TOKEN_SECRET` is set, use its raw UTF-8 bytes directly as the HMAC key on both sides.
2. Otherwise derive 32 bytes with HKDF-SHA256, empty salt, UTF-8 info `ig-link-token-v1`, and the shared link secret as input key material.
3. Without either secret verification fails safely. No identity is linked and no IG mileage or notification occurs.

| Purpose | LINE Harness binding | IG Harness binding |
| --- | --- | --- |
| Optional dedicated HMAC secret | `IG_LINK_TOKEN_SECRET` | `IG_LINK_TOKEN_SECRET` |
| Shared link secret / HKDF input | `IG_HARNESS_LINK_SECRET` | `LINE_HARNESS_LINK_SECRET` |
| Acceptance policy | `IG_LINK_TOKEN_POLICY` | Not used by issuer |
| Existing link notification URL | `IG_HARNESS_URL` | Not applicable |

Keep secrets in the deployment secret store, never in committed vars, URLs, or logs. The existing IG callback still requires `IG_HARNESS_LINK_SECRET` even when token verification uses a dedicated key. `iga` comes only from the signed payload when a valid token is present. `igan` remains an unsigned display label, not authenticated identity.

The LINE reference issuer is exported from `@line-crm/shared`:

```ts
// env is injected securely. Do not log the resulting token.
const igt = await issueIgLinkToken(env, igsid, businessAccountId);
const url = new URL('/r/' + encodeURIComponent(shortCode), lineWorkerUrl);
if (igt) url.searchParams.set('igt', igt);
```

The IG implementation uses the same call shape but reads `LINE_HARNESS_LINK_SECRET` for fallback. Pinned fixtures in `apps/worker/src/test-support/ig-link-vectors.ts` were generated by executing that IG implementation locally with a fake secret, a fixed clock, and nonce bytes 0 through 15. Tests cover both direct and HKDF keys independently of the LINE issuer.

## Policy and rollout

| Input | `off` (default) | `prefer` | `require` |
| --- | --- | --- | --- |
| Valid `igt` | Link + mileage | Link + mileage | Link + mileage, nonce ownership enforced |
| Only unsigned `ig` | Existing link + mileage behavior | Link, warn, **no IG return mileage** | Ignore, no link/mileage/notify |
| Invalid/expired/empty `igt`, with or without `ig` | No link/mileage/notify | No link/mileage/notify | No link/mileage/notify |
| Conflicting `ig` and valid `igt` | Token wins | Token wins | Token wins |

1. Apply pending migrations through **074**, then **075_ig_link_token_uses.sql**, and update LINE Harness while retaining `off`. Fresh installations use the regenerated bootstrap. `schema.sql` remains the historical base; the bootstrap generator applies the migration chain to it.
2. Configure the matching shared secret (or the dedicated token secret on both sides), then update IG Harness to emit `igt`.
3. Set LINE `IG_LINK_TOKEN_POLICY` to `prefer`. Monitor fixed warning codes: `[ig-link] unsigned_ig_param`, `[ig-link] invalid_token`, `[ig-link] replay_rejected`, `[ig-link] replay_storage_unavailable`, `[ig-link] cleanup_failed`. Logs do not contain token/secret values.
4. After confirming signed URLs work and unsigned traffic is understood, use `require`. Old unsigned DM links stop linking at this stage; their ordinary LIFF navigation continues. Cloud operators should coordinate both releases before enforcing it.

Rollback to `prefer`/`off` re-enables acceptance of unsigned identities and disables nonce enforcement; retain the table and secrets. Previously stored `friends.ig_igsid` values are not reviewed or cleared by this migration. A signed link is a bearer credential: forwarding a still-unused token can transfer its first claim. This feature does not prove possession of the Instagram account at click time. The separate raw `uid` cross-account flow is outside this change and still requires a separate security review.

## Replay storage and cost design

Spec text originally names migration 076. This branch uses **075** because the preceding finalized migration is 074. The table stores `nonce` (primary key), `friend_id`, `used_at`, and `expires_at`, with an expiry index. Only `require` claims the nonce, after LINE user authentication and before any IG link, mileage, metadata, or notification. Atomic INSERT-if-absent chooses one friend under concurrent attempts; a PK lookup permits the same friend to revisit. Storage failure skips IG linking. Existing friend-to-IG conflict checks and mileage's stable event identity remain in place.

| Entry / frequency | SQL calls × scope |
| --- | --- |
| Token verification / each supplied token | No SQL; one HKDF (fallback only) and HMAC verification, bounded input |
| `off` / `prefer` nonce handling | Zero nonce SQL |
| First valid `require` claim | 1 INSERT × one nonce PK (plus index maintenance) |
| Revisit or conflicting claim | 1 no-op INSERT + 1 SELECT × the same nonce PK; no new row |
| Existing link after acceptance | 1 friend PK UPDATE, at most 1 conflict SELECT; existing metadata, mileage and notification work remains |
| Cleanup / existing hourly Cron or DO tick | 1 indexed DELETE, at most 1,000 expired rows; no new schedule or retry loop |

For R valid require-mode arrivals/day and H hourly invocations/day, added nonce SQL is at most `2R + H`. A single hourly source normally gives H=24, and cleanup capacity is 24,000 expired rows/day. Concurrent Cron and DO sources multiply H; no distributed schedule lock is introduced. Cleanup processes bounded batches even after rolling back the policy. Greater expired volume can leave a backlog, but expired tokens are rejected before storage access. More users or arrivals scale statement counts linearly; retained rows grow with unique tokens and cleanup backlog.

Synthetic tests call the real helpers at 100, 10,000 and 100,000 unrelated records, check PK/expiry indexes, atomic claims, repeat visits and the cleanup cap, and measure SQLite VM instructions. The missing-expiry-index negative control must be substantially worse. `pnpm check:cost` includes these tests and existing cost safety checks. SQLite VM instructions are **not D1 billed rows**. Workers CPU, actual D1 read/write billing, shared account usage and monetary cost are unmeasured here, not zero. No production diagnostic scans, new paid service, notification destination, or automatic customer shutdown is added.
