# API / SDK の冪等キーとLINE送信の保証範囲

対象は `POST /api/friends/:id/messages`、タグ追加/解除、
`POST /api/conversions/track` の任意の `Idempotency-Key`（1〜255文字）。
SDK は対応メソッドの `idempotencyKey` を同ヘッダへ送る。
ヘッダなしの既存呼び出しは従来どおり毎回実行する。
CVの `fireEvent: true` はキー必須。新パラメータなしではイベントを発火しない。

## スコープ・保存期間

| 操作 | スコープ | 衝突を避ける方法 |
| --- | --- | --- |
| 個別送信 | `friend-message:<friendId>` | 同じ友だちへの各業務送信に別のキー |
| タグ追加/解除 | 共通の `friend-tag:<friendId>` | タグや操作が異なる要求に別のキー |
| CV記録 | 同じD1 DB全体の `conversion` | `integration:account:event` 等で呼出側が名前空間を付ける |

CVキーはLINEアカウント・呼出者・APIキー別には分離されない。
同じDBで別アカウントが同じキーを使うと、別内容は422になる。
DBが分離された環境間では独立する。認証・権限判定は従来どおり必要。

`api_idempotency_keys`（応答、要求ハッシュ、配信済みWebhook記録）と
`api_line_sends`（初回開始時刻、送信状態、送信先、固定したLINE本文）は
**無期限保持**。TTL/自動削除はない。5分はAPI処理の所有権リースであり保存期限ではない。
応答にはCVのmetadata等が、送信状態にはメッセージ本文が残る。
キーや履歴を削除して同じ要求を再投入すると新規処理として重複し得る。
削除/保持期限の導入は、未確定要求の隔離と再利用防止を別途設計してから行う。

## 状態・応答・復旧

- 完了したAPI要求：最初の2xx応答を `Idempotency-Replayed: true` で返す。
- 同じキーで入力が異なる：422。
- APIリース有効中：409。5分超で再取得しても、送信状態は別に保護される。
- キー付き送信の実行中：409、`code: "line_send_in_progress"`。
  生きている先行送信との重複を防ぐため、送信中状態にリース再取得はない。
  先行処理が完了すれば同じキーで結果を回収できる。
- 送信またはログ/完了記録が例外で失敗：初回開始時刻と本文を残す。
  初回から24時間未満に限り、同じ送信先・本文・LINE retry keyで再試行できる。
  同時に実行できるのは一つの送信処理だけ。状態更新は所有トークンで検査し、
  先行試行の遅れた書き込みが後続試行の状態を上書きしない。
- **初回送信開始から24時間以上（境界を含む）の未確定要求**：自動再送せず409、
  `code: "line_delivery_requires_review", requiresReview: true` を返す。
  25時間後でも追加送信しない。完了済みの要求は期限を超えても再生できる。
- 例外を記録できず処理が消失した場合も送信中のまま保持する。
  24時間以内は409、以後は要確認。安全に自動復旧できない不明要求を再取得しない。

SDK はエラー時に `LineHarnessError` を投げる。
`.status === 409 && .requiresReview === true`（`.code` も参照可能）なら
通常の再試行ループから外し、送信記録とLINE受理結果を運用者が確認する。
**新しいキーへの置換やDB行削除による強制再送はしない**。
未配信が確認でき、再送を判断した場合だけ別の業務操作として扱う。
本変更は手動解決APIや配信確認APIを追加しない。

キー付き自動化は操作ID＋イベント種別＋自動化ID＋アクション位置から安定した送信IDを作り、
同じIDをLINE retry keyとログIDに使う。再試行途中のテンプレート編集等がLINE本文を変えないよう、
最初に確定した本文を保存する。処理中の自動化アクションの並べ替えは避ける。
キー付きAPIイベントの送信はretry keyを使えるpushで行う（replyには適用しない）。
キーなしのreply/push分岐やbest-effortのログ動作は従来どおり。

[LINE公式の再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)では
retry keyは初回要求から24時間有効で、受理は利用者への到達を保証しない。
本実装は外部サービスへの全副作用のexactly-onceや、利用者への確実な到達を保証しない。
Webhookは成功後の記録前に障害が起きると重複し得るため受信側でイベントIDを排除する。
非送信アクションの失敗は従来の自動化ログに記録され、APIが完了する場合がある。
キー付き加点失敗と送信失敗はAPIへ伝播し、同じキーでの復旧を可能にする。

## DB変更・処理量の設計メモ

- `076_api_idempotency_keys.sql` と `077_api_line_sends.sql` を追加し、bootstrapを再生成済み。
  既存環境はキー付きAPIの利用前に両migrationの適用が必要。
  [D1 batchのトランザクション保証](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)で
  加点台帳INSERTとscore UPDATEを一体に確定する。直前INSERTの `changes()` が0なら加算しない。
- 入口はキー付きAPI要求/各自動化送信。初回送信は状態INSERT 1回＋完了UPDATE 1回、
  障害時はretryable UPDATE 1回。既存要求への衝突時はINSERT 1回＋PK SELECT 1回、
  再試行可能なら条件付きUPDATE 1回を追加。送信ログは送信あたり最大1行。
- 加点は1ルールにつき1 batch（INSERT＋UPDATEの2文）。ルール件数に比例し、
  台帳IDとfriend IDの主キーを使う。SUMによる履歴全走査やポーリング/Cronは追加しない。
- 送信状態の検索/更新は全て `id` 主キーに限定する。
  無関係な履歴を100/1000倍にしても対象行数は変わらない。履歴総量/ストレージは累積する。
  人数・頻度・送信アクション数が100/1000倍なら呼出し回数も比例する。
  日次回数は外部呼出側の頻度次第であり固定上限は追加しない。
- 合成SQLiteでproduction helperのSQL件数・主キー計画と100/1000倍の無関係行を検証する。
  `pnpm check:cost` も実行する。実D1課金rows・Workers CPU・本番の日次頻度は未測定。
  SQLiteの計画やVM命令をD1料金に換算しない。新しいポーリング・通知・停止設定は追加しない。
