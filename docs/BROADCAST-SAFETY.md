# 配信の送信元と失敗結果

配信時は保存された送信元アカウントを確認します。指定先が存在しない、無効、トークン未設定、DBで確認できない場合は送信しません。即時・予約・キュー・セグメント投入で同じ検証を使います。

旧形式の `line_account_id = NULL` は、登録アカウントのない従来環境に限り環境設定の送信元を使います。アカウントが登録されている環境では、1件だけでも送信元を推測しません。未指定の既存配信は止め、送信元と既配信の有無を確認してください。配信の本文・宛先を自動で付け替える処理や、既存データの削除は行いません。

単一アカウントの即時送信では、バッチ失敗時に後続バッチを中止し、LINEが受け付けた人数と失敗理由を残します。受付後の履歴・集計保存失敗や受付結果不明の配信を、自動再送できる下書きへ戻しません。DBが書き込めない場合も呼び出し側が送信ロックを解除しないようにします。

既存DBのstatus列は維持します。`sent` は処理終了を表すため、**成功判定にはlast_errorとsuccess_countも確認**してください。異常が残る配信は画面に「要確認」と理由を表示し、即時送信APIも502を返します。LINEの受付人数は端末への到達を保証する人数ではありません。

キュー送信は従来の進捗と再試行キーを維持し、失敗理由を表示します。一般バッチの送信ログ保存失敗は、受付人数を失わず完了後にも表示します。個別化送信の受付後ログ保存失敗も、LINEによる拒否とは区別します。

## 通常キュー multicast の未確定バッチ

通常キュー multicast は、LINEへ送る前に `pending_batch_id` と `pending_batch` へ宛先・本文・再送キー・送信元・最初の試行時刻を保存します。受付結果が不明な場合は計画を保持し、同じ宛先と本文で再試行します。新しい対象者が先頭に増えても、その人を未確定バッチへ混ぜません。保存したバッチの受付を確認してから、未送信者へ続けます。

計画保存に失敗した場合は送信しません。対象者が対象外になった、送信元/本文が変わった、計画が破損した場合は計画を残して自動送信を止め、既存の `last_error` に確認が必要な理由を表示します。LINEは再送キーを24時間管理するため、本実装は余裕を取り最初の試行から23時間で自動再試行を停止します。期限切れを新しいキーで自動再送しません。

ログ・受付人数・計画の消費は同じDB transactionで保存し、古い実行が後から戻っても同じ計画の受付を二重計上しません。受付後にログ保存だけが失敗した場合は、既存の「受付人数を保持して再送しない」動作を保ちます。DB進捗も書けない場合は元の計画を残します。保存済みの受信者情報を管理APIの応答へ追加しません。

DB transactionの保存は完了したものの応答だけ失われた場合は、計画が消費済みでもロックが残ることがあります。3分以上経過し、通常配信の受付人数とテスト送信を除く重複のない送信ログが完全に一致する場合だけ、その人数から再開します。ログ不足・重複・受付人数だけの保存では自動復旧しません。

完了処理も、受付人数が自分の保存済み件数と一致し、別の未確定バッチがない場合だけ実行します。集計待ちレコード・完了状態・送信結果を同じtransactionで保存するため、遅れて戻った古い実行が新しい計画や完了結果を消しません。

予期しないDB例外の理由保存も、現在のロック時刻・状態を照合します。保存済みの完了結果や新しい実行の理由欄を、古い実行から書き換えません。現在の実行で起きたエラーは記録し、ロックを勝手に解除しません。時刻は従来と同じnaive JST形式を保ちます。

ログ保存は40人ずつのSQLへまとめます。1文88パラメータ以下で、D1の1文100パラメータ制限を超えません。500人分は最大13文のログINSERTと進捗UPDATE1文で原子的に保存します。

過去の受付結果不明の配信に保存済み計画がない場合は、元の宛先・本文を推測して自動再送しません。過去のログ、件数、本文は補正せず、確認が必要な状態で止めます。

### 適用時の前提

新しいWorkerを動かす前に `NNN_broadcast_pending_batch.sql` の適用が必要です。旧Workerはこの計画を理解しないため、運用では旧版の実行中ジョブがない状態を確認して移行します。計画が残ったまま旧版へ切り戻してcronを動かすことも避けてください。この変更の検証ではローカルDBだけを使用し、リモートDBへの移行やデプロイは行っていません。

## 名前入りキュー配信の再開と重複記録

名前入り配信は、現在の対象者一覧を保存済みの友だちIDで既送・未送に分け、未送の順序と1回10人の上限を保って再開します。配信済みの人がブロック/タグ解除した場合や、新しい対象者が先頭へ増えた場合も、古い一覧の番号だけで未送の人を飛ばしません。

取得したロック時刻を、送信直前の確認・送信記録・上限停止・失敗/進捗保存・完了処理で照合します。復旧後に古い成功/失敗応答が戻っても、新しい実行の記録や結果を上書きしません。ロック時刻は従来と同じnaive JSTとし、既存の3分の復旧判定を保ちます。送信記録は同じ配信/友だちの実送信ログがない場合だけ追加し、過去の重複記録を自動補正しません。

予期しないDB例外の理由を表示する場合も、取得したロックを照合します。保存済みの完了結果や新しい実行の理由欄を、遅れて戻ったエラーで上書きしません。自分の処理で起きたエラーは従来どおり記録し、ロックを勝手に解除しません。

完了状態と集計待ちレコードは同じtransactionで保存します。新しいschema/migrationは不要です。旧版はこれらの書き込み条件を持たないため、適用時には旧版の実行中ジョブを終えてから切り替える必要があります。この作業では本番反映・実LINE送信を行っていません。既存の再試行キーと対象/アカウント条件は維持し、既に始まった外部リクエストは取り消しません。

送信直前に、既存の `dedup_progress` 欄へ個別化キュー専用のversion付きリクエストを保存します。送信先・本文・再試行キー・集計単位・最初の試行時刻を固定し、トークンは保存しません。受付結果不明の場合は保存内容を維持し、同じ対象者の同じ内容を23時間未満に限って先に照合・再試行します。名前、LINE ID、アカウント/チャネル、本文、LIFFや対象条件が変わった場合、対象者が外れた場合、保存内容が壊れた場合、時刻が未来または23時間以上の場合は「要確認」で自動送信を保留します。新しいキーへ付け替えません。

受付ログとリクエストの消費は同じDB transactionにまとめます。commit後に応答だけ失われても、その実行が作ったログIDとロックを確認できた場合だけ継続します。未確定のリクエストが残る間は完了処理を禁止します。確認済みの接頭部分や未確定リクエストがある配信を初回扱いしてリンクを再生成したり、月間上限不足で下書きへ戻したりしません。保存済みリクエストを照合した後、新しい送信へ進む前には通常の上限確認を行います。1回10人の枠は維持します。

未確定リクエストも、既存の友だち・月間使用量上限を超えていればAPIを呼ばず保存計画を保持します。上限停止で初回試行時刻を更新しないため、上限解除後に23時間以上過ぎていれば要確認で止めます。照合した受付ログで使用量が上限に達した場合も、続く新規送信の前に止めます。

この記録は新しいコードから始まります。旧版で既に受付結果不明になった配信の最初の試行時刻・本文は復元できません。切り替え前に旧Workerを排出し、旧未完了配信を完了または受付照合する必要があります。未確定記録を旧版が読めないため、保留中の配信がある状態で旧版へ戻さないでください。既存status/API/schemaや過去の台帳は補正しません。受付409を成功扱いするには受付済みリクエストIDを検証するSDK修正（PR #394）が前提です。1人ごとに送信前の保存と受付ログとのtransactionが増えるため、DB書き込みコストは増えます。

保存計画がなく、旧エラー欄に「受付結果不明」または「受付済みだが記録失敗」が残る配信は、現在の本文で新しい初回試行を作らず要確認で保留します。既知の履歴・件数も変更しません。LINEを呼ぶ前の準備・計画保存失敗は別の理由で記録し、この旧受付不明の保留と混同しません。旧エラー欄にも証拠のない未完了配信は自動判別できないため、導入前の運用照合は引き続き必要です。

この旧形式の保留は送信元や履歴の照会より先に判定します。別の照会エラーが受付不明の理由を上書きし、後から再送可能にしてしまうことを防ぎます。保留理由の保存自体が失敗しても元の理由を残して送信を止め、同じ保留ラベルへの書き込みは繰り返しません。

## 複数アカウント配信を中断後に再開する場合

複数アカウント配信は、LINEを呼ぶ前に既存の内部列`dedup_progress`へ送信計画を保存します。通常multicastは最大500人、名前入りpushは1人の実リクエストを保存します。計画には送信方式・送信元とチャネルID、論理人物ID・友だちID・LINE ID、名前の展開や本文の微調整を含む実リクエスト、集計単位、初回時刻、再送キーを含めます。トークンは保存せず、管理APIの返却項目も増やしません。スキーマ変更はありません。

応答の消失や5xxなどで受付が不明な場合は、完了にせず計画を保持して次のキュー処理へ戻します。次回は新しい対象者を処理する前に、保存した対象・本文・キーで再試行します。明確な4xx拒否（409を除く）ではそのアカウントを失敗として記録し、他のアカウントを続行します。受付済み409の判定はPR #394を前提とします。

LINEの重複抑止期限は24時間なので、安全余裕を取り初回から23時間以上の計画を再送しません。未来の時刻、破損、本文・表示名・LIFF ID・チャネル変更、未フォロー、対象タグの喪失、重複排除の勝者変更があれば、計画を残して要確認にします。名前が変わった場合も、新しい本文でキーを作り直しません。別アカウントへの付け替えや過去の台帳補正は行いません。

受付履歴と進捗は一つのDBトランザクションで保存します。500人分は40人ごとのINSERTへ分け、各SQLのバインド数を100未満にします。保存前・保存失敗・完了確定は送信計画を含む進捗全文と処理状態で条件付けし、古い実行から新しい計画や完了結果を消さないようにします。完了と集計の作成も同じトランザクションです。

名前入りpushは1人の受付ごとに履歴と進捗を保存します。途中の1人だけが受付不明なら、それまでに確定した人を送り直さず、その1人を同じキーで照合してから続けます。明確な拒否では、それまでの受付人数を保持して当該アカウントを中断します。従来の10人ごとの時間/使用量チェックと待機を保ちますが、送信計画の保存により1人あたりのDB書き込み回数は増えます。保存サイズ上限などで計画を保存できない場合は、LINEを呼ぶ前に止めます。履歴を持たない旧進捗は推測で補いません。

会員登録や連携によって、配信済みの人の論理IDが`solo:friend`から`uid:user`などへ変わる場合があります。再開時には、対象配信・選択済みアカウント内のテストを除く送信履歴を1回だけ読み、保存済み受付人数と重複のない友だち別履歴が完全に一致するときだけ、同じ友だちの現在の論理IDも既送として照合します。別アカウント側が当選者になった場合も、その同じ人を追加送信しません。別名を受付件数へ足したり、過去の履歴・ID・件数を書き換えたりはしません。現方式の進捗で履歴不足・重複・送信元不一致があれば要確認で停止します。証拠の揃わない旧進捗の別名を推測しません。プレビューSQLのID優先順は維持します。

予期しないDB例外の理由も、自分が最後に保存した進捗と現在の処理状態が一致する場合だけ保存します。自分の現在のエラーを表示しつつ、別の送信計画や完了結果の理由を遅延した例外で上書きしません。

リリース時はPR #394（受付済み409）、#120（キューの古いスナップショット拒否）、#123（配信開始と競合する編集の拒否）との統合を確認し、古いWorkerの実行を停止・排出してください。旧コードは保存計画を理解しないため、未確定の計画を持つ配信が残る間は旧コードへ戻さないでください。計画保存前に生じた受付不明の配信、欠落した履歴、既存の重複履歴を自動で復元・修正する機能ではありません。既に始まった外部リクエストを取り消す処理でもありません。

導入前の未完了行には、最初の試行時刻や未記録の受付を証明する情報がない場合があります。旧処理の完了、または受付状況の手動確認を済ませてから切り替えてください。旧進捗の既知のIDは従来どおり扱いますが、不明な受付を安全に再構築する保証はしません。
